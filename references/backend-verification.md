# 后端实战核验：围绕一个真实项目

目标不是考框架名词，而是区分：本人能负责服务，还是只演示过界面/拼过工作流。建议30–40分钟，HR负责约定，技术面试官判答案。允许使用Agent，但回答必须落到自己项目和可验证证据。

先问：“挑一个你本人已经交付的ERP或AI服务。从用户点按钮，到后台处理、数据库写入、返回结果，完整走一遍。哪些由你实现，哪些复用？”让候选人画简单链路，再根据该链路追问，不预先喂答案。

| 追问 | 有价值的证据 | 警示信号（不是单独自动淘汰理由） |
|---|---|---|
| 选一个实际接口，输入输出是什么？对应哪些表？你改了哪个模块？ | 脱敏接口、schema、代码/提交或明确可解释的实现 | 只有页面截图，始终说“AI/平台会处理”，无法区分本人和团队 |
| 同一请求发两遍，或者上游超时但实际成功，会发生什么？ | 能说明自己系统如何避免重复扣费/建单、如何查询与补偿、哪里仍有限制 | 只说重试，不考虑重复业务动作 |
| 用户A把请求中的订单ID换成用户B的，会怎样？ | 服务端核验身份和资源归属；说明权限检查位置 | 只隐藏前端按钮或只检查是否登录 |
| 第三方API密钥存哪里？日志会不会打印？员工离职如何撤销？ | 服务端凭据管理、日志脱敏、权限最小化与撤销路径 | 把生产密钥放网页/仓库；要求面试官查看真实密钥 |
| 最近一次故障怎么发现、定位、恢复？怎么防止再发生？ | 脱敏日志/时间线、监控、回滚/修复、回归测试；没有生产故障时用测试失败案例 | 只有“重启就好了”，无法说明数据是否受影响 |
| 新增一个需要改表结构的功能，怎么上线而不破坏旧数据？ | 能解释迁移、兼容、备份/恢复、测试与回滚的取舍 | 直接手改生产表且无验证/恢复考虑 |
| 某段代码由Agent写的，你如何确认它正确？现场指出一处你改过的错误。 | 找到真实代码/测试、解释边界和修复 | 只说模型足够强，不知道如何验证 |

## 可选短实操（另行约定，不要求免费生产开发）

给脱敏或虚构订单JSON与一个本地模拟接口，允许候选人使用Codex/Claude Code及文档，在约45分钟内实现一个小服务：写入订单、查询本人订单，并处理重复提交。约定小范围，不要求搭完整基础设施。

验收关注：
- 同一订单重复提交不会重复产生业务记录。
- A用户不能读取B用户订单；检查在服务端。
- 上游故障有明确状态，不静默丢失/伪造成功；不要求复杂消息队列。
- 至少一个失败路径测试，能解释部署和密钥放置方式。
- 能解释哪些由Agent生成、哪些由本人审查/修改。

不按打字速度、记忆语法或手写代码量评分；HR不凭术语数量打分。保密限制可用脱敏示例、自己拥有的项目或上述模拟任务替代，不索取前雇主源码、客户数据、生产账号或密钥。

## 结论口径

- 足够证据：能解释本人实现、展示对应证据、处理一个故障边界；可满足轻量后端岗位门槛，并不自动证明大型分布式架构能力。
- 待核验：演示有功能，但关键实现归属或数据/权限边界说不清；记具体缺口。
- 不符合：经追问/实操明确没有相关实现能力或没有实际负责过后端；不要仅凭没有后端职称作结论。
